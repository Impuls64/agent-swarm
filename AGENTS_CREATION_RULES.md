# Правила создания AGENTS.md

> Базируются на спецификации Addy Osmani (Agent Engineer, урок 15)
> и анализе 2500+ репозиториев с AGENTS.md

## Архитектура: Orchestrator + Workers + per-project AGENTS.md

### Глобальный уровень (~/.agents/)

```
~/.agents/
├── master.md              # Оркестратор: Router, карта воркспейса, глобальные грабли
├── LESSONS.md             # Лог ошибок/решений (дописывать грабли)
├── AGENTS_CREATION_RULES.md  # Этот файл (спецификация)
├── swarm.sh               # Справочник workers (list)
└── workers/               # Доменные модули — читать ТОЛЬКО нужный по Router'у
```

Загрузка: `master.md` + `LESSONS.md` подключены через `instructions` в
`~/.config/opencode/opencode.jsonc` — грузятся в КАЖДУЮ сессию автоматически.
Workers в контекст не грузятся: оркестратор читает файл по Router-таблице,
когда задача попадает в домен. Никакого codegen/активации — правишь файл,
перезапускаешь opencode.

### Уровень проекта (один файл на проект)

```
~/bot/AGENTS.md            # Команды, стек, структура, грабли проекта
~/work/news-parser/AGENTS.md
```

**Один AGENTS.md в корне проекта.** Вложенные `backend/AGENTS.md` НЕ работают:
OpenCode читает только ближайший AGENTS.md вверх по дереву + глобальный
`~/.config/opencode/AGENTS.md` (см. доки opencode «Rules»). Для монорепо
с разными стеками — разделы внутри одного файла или отдельные проекты.

### Оркестратор (master.md)
- **Роль**: Tech Lead / Coordinator
- **Не пишет код** — маршрутизирует по Router'у, делегирует через task tool
- **Проверяет качество** по Quality Gates
- **≤150 строк** (критически важно для context window)
- Грузится глобально через `instructions` — правка влияет на ВСЕ сессии

### Workers (workers/*.md)
- **Роль**: Domain Expert
- **Пишет код** по правилам домена
- **Следует Karpathy Guidelines**
- **Читается по требованию** по Router'у в master.md, не грузится автоматически
- **≤200 строк** (workers/osengine.md — исключение, 528 строк; не подключать в instructions)

## 6 основных областей (для каждого Worker)

### 1. Commands (Команды)
**Что**: Точные команды для сборки, тестов, линтинга.

**Плохо:**
```
- Линтинг: ruff
```

**Хорошо:**
```
- Линтинг: uv run ruff check . --fix
- Тест одного файла: uv run pytest tests/test_api.py::test_create -v
```

### 2. Testing (Тестирование)
**Что**: Фреймворк, структура, naming conventions.

**Плохо:**
```
- Используем pytest
```

**Хорошо:**
```
- pytest + pytest-asyncio для async
- Тесты зеркалят src: src/api/users.py → tests/api/test_users.py
- Fixtures: tests/conftest.py
- Покрытие: >80% для нового кода
```

### 3. Project Structure (Структура)
**Что**: Карта директорий. Где что находится.

**Плохо:**
```
- Код в src/
```

**Хорошо:**
```
- `src/api/` — REST endpoints (FastAPI)
- `src/core/` — бизнес-логика (чистая, без фреймворков)
- `src/db/` — SQLAlchemy + Alembic миграции
- `tests/` — зеркалит src/
```

### 4. Code Style (Стиль кода)
**Что**: Naming, форматирование, паттерны. **Примеры кода лучше слов.**

**Плохо:**
```
- Используй type hints
```

**Хорошо:**
```python
# Плохо
def process(data):
    ...

# Хорошо
def process_user_data(raw_data: dict[str, Any]) -> ProcessedResult:
    ...
```

### 5. Git Workflow (Git)
**Что**: Branching, commits, PR requirements.

**Пример:**
```
- Branch: feat/, fix/, chore/ префиксы от main
- Commits: conventional commits (feat:, fix:, docs:)
- PR: squash merge, CI проходит, 1 approval
```

### 6. Boundaries (Границы)
**Что**: Что НЕЛЬЗЯ трогать. **Самая важная секция.**

**Пример:**
```
## Do Not Modify
- `.env` — секреты, никогда не коммитить
- `migrations/` — только через alembic revision
- `vendor/` — third-party, managed externally
```

## Золотые правила

### 0. Переносимость путей

`~` — раскрытие оболочкой, а не путь в ФС:

- В тексте AGENTS.md — `~/project/file`, **никогда** `/home/<user>/...`: инструкция сломается на другой машине
- В скриптах — `"$HOME/project/file"`, не `~` (нужно для cron/systemd и неинтерактивного шелла)
- Пути **внутри** Docker (`/home/node/.n8n`, `/usr/local/...`) не трогать — они про контейнер, а не про хост
- В WSL: `~` — это Linux-юзер внутри WSL, Windows-дерево в `/mnt/c/...`
- В вызовах инструментов агента (read/glob/grep) — абсолютный путь: `~` не раскрывается и приводит к поиску `/home/<user>/~/...`

### 1. Лаконичность
- **Master (AGENTS.md)**: ≤150 строк
- **Workers**: ≤200 строк (по возможности)
- Длинные файлы теряют важную информацию в context window

### 2. Конкретика
- **Bad**: "Мы используем современный JavaScript"
- **Good**: "React 18.2 + TypeScript 5.3 + Vite 5.0"

### 3. Примеры кода
- Один пример стоит 10 абзацев текста
- Показывай **good** и **bad** варианты

### 4. Итеративность
- Начни с минимума (Commands + Structure)
- Добавляй правила, когда агент ошибается
- Лучший AGENTS.md растёт через итерации, не планирование

### 5. Как код
- Обновляй в том же PR, что и изменения
- Устаревшие инструкции хуже, чем их отсутствие

### 6. Объясняй "почему"
- Для неочевидных правил добавь пояснение
- Пример: "Не используй datetime.now() напрямую → используй src/core/clock.py для контроля времени в тестах"

## Иерархия для монорепо

```
repo/
  AGENTS.md              # Общее: команды, git, границы
  packages/api/          # Разделы внутри AGENTS.md для Python-специфики
  packages/web/          # Разделы внутри AGENTS.md для TS-специфики
```

Вложенные AGENTS.md OpenCode не читает — спецификация по стеку живёт в секциях одного файла. Альтернатива: разнести подпакеты в отдельные проекты.

## Quality Gates (чеклисты Master)

### Code Review
- [ ] Код соответствует стилю домена
- [ ] Нет хардкода секретов
- [ ] Обработка ошибок (не silent except)
- [ ] Type hints / аннотации
- [ ] Логирование вместо print
- [ ] ≤88 символов в строке

### Architecture
- [ ] Разделение ответственности
- [ ] Чистая архитектура (core отделён от фреймворка)
- [ ] Тестируемость
- [ ] Нет циклических зависимостей

### Security
- [ ] Секреты в .env
- [ ] Валидация входных данных
- [ ] Защита от инъекций
- [ ] CORS настроен (для web)

## Workflow создания нового проекта

### Шаг 1: Создать папку проекта

```bash
mkdir -p ~/work/my-project   # или ~/projects/
```

### Шаг 2: Написать AGENTS.md в корне проекта

Шаблон (6 секций, команды — первыми):

```markdown
# AGENTS.md — <Название проекта>

<1-2 предложения: что делает, точка входа>

## Команды
- запуск: `...`
- тест: `...`
- линт: `...`

## Стек
- <Язык/фреймворк>: <версия>

## Структура
- `dir/` — назначение

## Границы
- ✅ Всегда: ...
- ⚠️ Спросить перед: ...
- 🚫 Никогда: ...
```

### Шаг 3: Дополнить по мере ошибок

- Добавляй правила, когда агент ошибается; грабли проекта — в AGENTS.md проекта, грабли окружения — в `~/.agents/LESSONS.md`
- Дописать проект в карту воркспейса в `~/.agents/master.md`

### Пример: структура файла моно-проекта

```
~/work/my-project/
├── AGENTS.md              # Единственный файл: команды, стек, структура,
│                          # секции по доменам (Python/Frontend/DevOps), границы
│                          # ≤150 строк
├── backend/               # код, AGENTS.md здесь НЕ нужен и не читается
└── frontend/
```

Для крупных проектов с разными стеками — либо секции внутри AGENTS.md с
якорями по путям (`backend/:` …), либо разделить на отдельные проекты.

### Как opencode читает AGENTS.md

OpenCode при старте ищет правила в порядке:

1. **Локальный** — ближайший `AGENTS.md` вверх по дереву от cwd (первый найденный выигрывает; `CLAUDE.md` — fallback если AGENTS.md нет)
2. **Глобальный** — `~/.config/opencode/AGENTS.md` (применяется всегда, дополняет локальный)
3. **Claude Code** — `~/.claude/CLAUDE.md` (fallback)

**Важно:** вложенные AGENTS.md в подпапках проекта НЕ читаются (это поведение Cursor/Copilot, не OpenCode). Один проект = один AGENTS.md в корне.

Дополнительные файлы подключаются через `instructions` в `opencode.json` (поддерживаются пути и URL, файлы комбинируются с AGENTS.md).

## Формат секций

### Стандартная структура AGENTS.md проекта

```markdown
# AGENTS — [Проект] ([стек])

## Команды
- Запуск: `...`
- Тест: `...`

## Стек
- **X**: version

## Структура
- `dir/` — description

## Стиль кода
```python
# Пример
```

## Тестирование
- Framework: ...

## Границы (трёхуровневые)
- ✅ **Всегда**: прогонять тесты перед коммитом, секреты в .env
- ⚠️ **Спросить перед**: сменой схемы БД, правкой конфигов, удалением файлов
- 🚫 **Никогда**: хардкод секретов, bare except, push в main
```

Трёхуровневые границы (Always / Ask first / Never) — самая эффективная форма: предотвращает разрушительные ошибки лучше длинных списков «Запрещено».

## Примеры хороших файлов

### Master (AGENTS.md) — ~100 строк
```markdown
# AGENTS.md — Orchestrator

## Роль
Tech Lead. Маршрутизирует задачи по Router'у, делегирует через task tool.

## Router
| Домен | Worker |
|-------|--------|
| Python | ~/.agents/workers/python.md |
| Frontend | ~/.agents/workers/frontend.md |

## Карта воркспейса
- `~/bot/` — ... (AGENTS.md есть)
- `~/work/x/` — ... (AGENTS.md нет → README)

## Quality Gates
- [ ] Code Review: стиль, ошибки, типы
- [ ] Architecture: чистота, тестируемость
- [ ] Security: секреты, валидация

## Запрещено (глобально)
- `import *`
- `except:` без типа
- Хардкод секретов
```

## Обновление существующих файлов

При обновлении Worker'ов:
1. Добавить секцию **Commands** с точными командами
2. Добавить секцию **Testing** с конкретикой
3. Добавить секцию **Boundaries** (Do Not Modify)
4. Убрать абстрактные описания, заменить примерами
5. Сократить до ≤200 строк
6. Добавить "почему" для неочевидных правил
